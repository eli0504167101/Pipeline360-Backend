# User Authentication

Phase 2 adds user accounts and MongoDB-backed sessions only. Existing reservation
routes remain public and unchanged; they do not yet enforce account ownership.
There are no Premium actions, booking history endpoints, frontend screens, or
infrastructure changes in this phase.

## Configuration and startup

`npm start` validates authentication configuration before opening the HTTP server.

| Variable | Requirement |
| --- | --- |
| `AUTH_ENV` | Required: `local`, `demo`, or `production` |
| `AUTH_ORIGIN` | Required exact browser origin: scheme, hostname, optional port; no slash/path/credentials |
| `AUTH_TRUSTED_PROXIES` | Optional comma-separated explicit IP addresses or nonzero CIDRs; defaults to trusting no proxy |
| `MONGO_URL` | Existing required database connection setting |
| `PORT` | Existing HTTP port; defaults to `3000` |

`demo` and `production` require an HTTPS origin. `local` allows only `localhost`,
`127.0.0.1`, `[::1]`, or `hotel.local`; it cannot be combined with
`NODE_ENV=production`. Local HTTP cookies use the separate name
`p360_local_session`. HTTPS uses `__Host-p360_session`, `Secure`, `HttpOnly`,
`SameSite=Lax`, `Path=/`, and no `Domain` attribute. Cookie security is derived
from validated configuration, not caller-controlled forwarded headers.

For local development only, run from the Backend repository with an isolated
local MongoDB database and set `AUTH_ENV=local`, `AUTH_ORIGIN` to the actual
browser origin (for the existing local access path, `http://hotel.local:3000`),
and `MONGO_URL` through your environment. Then run `npm start`. Never put real
connection credentials in Git, command examples, logs, or PR descriptions.

All replicas must use the same origin, cookie settings, database, and synchronized
clocks. Sessions and rate counters are persisted in MongoDB, never process memory.
No sticky sessions or shared signing secret are required. Authentication writes use
majority write concern. Password hashing has a per-process concurrency bound; this
is a resource safeguard, while the authentication attempt limit is database-shared.

The server preserves liveness while connecting to MongoDB. Readiness and auth
routes remain unavailable until unique/TTL index initialization succeeds. Database
errors return generic `503` responses without connection strings or error details.
The reservation API retains its existing error behavior.

## API

Every auth response has `Cache-Control: no-store`. Auth routes do not enable CORS.
All state-changing auth requests require the exact configured `Origin`, must not
have `Sec-Fetch-Site: cross-site`, and require `Content-Type: application/json`.
Requests without `Origin`, including command-line clients, must explicitly supply it.
The JSON body limit is 8 KiB. Unknown fields are rejected.

| Method | Endpoint | Request / result |
| --- | --- | --- |
| POST | `/api/auth/register` | `{ fullName, email, password }`; `201` with `{ user }` and session cookie |
| POST | `/api/auth/login` | `{ email, password }`; `200` with `{ user }` and a fresh session cookie |
| GET | `/api/auth/me` | Valid session required; `200` with `{ user }` |
| GET | `/api/auth/csrf` | Valid session required; `200` with `{ csrfToken }` |
| POST | `/api/auth/logout` | Valid session, JSON `{}`, and `X-CSRF-Token` required; `204`, deletes session and clears cookie |

A public user contains only `id`, `fullName`, `email`, and `subscriptionTier`.
Registration explicitly writes `free`, ignoring no fields silently: submitted tier,
user ID, or hash fields cause `400`. There is no API for changing membership.
Passwords, password hashes, and session identifiers are never returned in JSON.
The session identifier is transmitted only as an HttpOnly Set-Cookie value.

Names are trimmed and limited to 120 characters. Emails are trimmed/lowercased,
validated, and limited to 254 characters; a unique database index prevents races.
Passwords are not trimmed, must have 12–128 characters and at most 256 UTF-8 bytes.
Hashes use asynchronous scrypt (`N=32768`, `r=8`, `p=1`, 32-byte output) and a random
16-byte salt. Verification uses timing-safe comparison and runs scrypt for unknown
users as well. One hash operation runs per process at a time (approximately 32 MiB
scrypt working memory); concurrent hashing requests receive `503` instead of queuing.

Login rotates the identifier and invalidates an existing cookie's session after
successful credential verification. Other sessions for the user remain valid.
Sessions have a fixed eight-hour absolute expiry, with no sliding renewal. Each
request checks `expiresAt > now` explicitly; asynchronous TTL cleanup is not an
expiration guarantee. Deleted users cannot authenticate with their old sessions.
Logout revokes the current session in MongoDB, including access through other replicas.

Session IDs are random 32-byte values generated by `crypto.randomBytes`; MongoDB
stores only their SHA-256 hashes. CSRF proof is domain-separated SHA-256 of the
session identifier and is returned only by the authenticated `/csrf` endpoint.
It is not a login credential and must be supplied in the `X-CSRF-Token` header
on logout. A proof from another session is rejected. Login/registration are protected
against login CSRF through exact origin checks and JSON-only requests.

Expected errors: invalid input `400`, duplicate email `409`, invalid credentials or
session `401`, invalid origin/CSRF `403`, invalid media type `415`, oversized body
`413`, exceeded attempt budget `429` with `Retry-After`, unavailable auth/database
or saturated password hashing `503`.

## Shared rate limiting

Login and registration share a fixed 15-minute budget: 60 attempts per source IP
and 10 per normalized email, including successful and malformed credential attempts.
Counters use atomic MongoDB `$inc` operations and unique `_id` keys, with duplicate
upsert retry. Limits survive application restarts and apply across all five replicas.
A bucket ID hashes the scope, value, and time window; raw email/IP values are not
stored in rate records. TTL removes old buckets; the current window is chosen by
server time, independently of cleanup. Fixed-window limits permit bursts around a
window boundary. Email/IP hashes are pseudonymous, not anonymous.

Without trusted proxies, all clients behind an Ingress may share one IP budget.
Before deployment, identify the actual trusted proxy IP ranges and verify that the
last trusted proxy overwrites forwarded headers. Never use unrestricted proxy trust.
Rate limits cannot replace network-level protection against distributed abuse;
email-based limits can also be abused to deny a victim login temporarily.

## Automated validation

Run from the Backend repository:

```bash
npm ci
npm test
```

- `npm run check`: syntax-checks all source, test, and script JavaScript.
- `npm run test:api`: the existing 42 reservation/health regression tests.
- `npm run test:auth`: configuration/password tests and actual MongoDB integration.

Integration tests use `mongodb-memory-server-core` to start MongoDB `7.0.24` on
loopback with a private temporary data directory. They never read `MONGO_URL`, never
accept an external URI, and delete only their own test collections. Cleanup stops
the process and disconnects Mongoose even after test failures. A missing MongoDB
binary/download is a test failure, not a skipped integration suite.

Downloaded binaries are cached under the OS temporary directory, outside the
repository and Jenkins workspace so they cannot enter the production Docker image.

The first run needs network access to the official MongoDB binary download host,
a writable binary cache/temp directory, local port binding, and compatible Linux
libraries (including OpenSSL). No Docker daemon, cluster, database credentials, or
existing MongoDB instance is used. GitHub Actions and Jenkins retain their existing
`npm ci && npm test` flow; the integration suite is included by the npm test script.

Tests validate unique indexes, normalized duplicate registration, concurrent writes,
persisted password/session hashes, expiration before TTL cleanup, database reconnect,
five independent Express app instances using the same database, logout revocation,
CSRF separation, missing/invalid sessions, production cookies, shared atomic limits,
forwarded-header spoof rejection, and fail-closed behavior during database failure.
The five app instances share one test process; live load-balancing, failover, TLS
termination, and MongoDB replica-set majority availability still need deployment tests.

## Deployment prerequisites and limits

This PR must not be deployed with existing configuration alone: `AUTH_ENV` and
`AUTH_ORIGIN` are new required values. Add them later through a separately reviewed
Infrastructure PR. Do not merge Infrastructure PR #50 as part of this work.

- Use HTTPS termination before real accounts; local HTTP is for development only.
- Use separate Demo and Production database names/credentials and matching origins.
  This code does not create separate environments or enable any demo upgrades.
- Apply the existing Kubernetes Secrets approach if connection credentials are added;
  there is no new application signing secret to distribute.
- Enable and review MongoDB authentication, least-privilege permissions, backups,
  and network access restrictions before production. The current local database
  setup does not establish production security.
- All five replicas require access to the same environment-specific collections:
  `users`, `sessions`, and `authratelimits`. Confirm index creation permissions and
  resource usage under the existing CPU/memory limits.
- Deployments must verify trusted proxy topology, real browser cookies, CSRF,
  rate limits, and revocation across separate processes/Pods before release.
- Existing reservation lookup/cancellation remain public until a later approved
  ownership phase. Do not describe this phase as protecting reservation data.
- Email ownership verification, password reset, MFA, account-wide session revocation,
  and account deletion are not implemented. Duplicate registration discloses whether
  an email is registered, as required by the current duplicate rejection contract.
- Already-authorized in-flight requests may finish while logout is processed.

Compatible dependency updates resolve advisories reported during implementation in
`proxy-addr`, `qs`, and `body-parser`; Express remains on major version 4. Rerun
`npm audit` during review because advisory data changes over time.
